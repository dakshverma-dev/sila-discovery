# Sila Gate B (P0 01–P0 06) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** One complete, secure ordinary booking through Sila — venue publishes a dated session, a club organiser requests, the venue approves, the organiser commits conditionally, payment opens at a staffed 11:45 release, the venue records the receipt and confirms — with the two-club commitment rules already enforced.

**Architecture:** New `sila` Postgres schema (tables, RLS on, no policies) with guarded `sila_api` security-definer functions executed by the existing least-privilege `scb_app` login. Pure rules stay in `lib/sila/*` (already built and tested); database functions repeat consequential checks under row locks with the same error codes. A thin server command layer (`lib/sila/commands/*`) is the single entry for both `/api/v1/sila/*` route handlers and the pages' server actions. Supabase Auth email links identify people; venue roles come from invited email. The hackathon `scb` schema and pages stay untouched until a later plan removes them.

**Tech Stack:** Next.js 16.4 (App Router), React 19.3, TypeScript 6, zod 4, pg 8, @supabase/ssr 0.12 + supabase-js 2, Supabase local stack (Postgres, Auth, Mailpit on 54324), Vitest 5, Playwright 1.64 + axe.

**Spec:** `docs/Sila_Product_Trial_and_Build_Guide.md` (transcription of the canonical `docs/Sila_Combined_Product_Trial_and_Build_Guide.pdf`). Section numbers below are Part II unless marked "Part I". Engineering rules: `AGENTS.md`.

## Global Constraints

- Times: venue zone `Europe/London`; store `timestamptz` (UTC instants). Every datetime typed into a form is London wall time converted with `fromLocal` from `lib/sila/time.ts`, never `new Date(string)`.
- Money: GBP integer minor units. Totals and deposits are computed on the server only: deposit = `floor((total * deposit_bp + 5000) / 10000)`, balance = total − deposit (§18). Never trust a client total.
- At most two clubs per session; minimum ≤ capacity; payment window ≥ 5 days; final decision ≥ 7 calendar days before the event; maximum wait 21 calendar days from commitment to final decision (§07, §12, §23).
- Commit at `fill_by` is allowed; after it is rejected (§12). Invitations/approvals reserve no capacity (§04, §15).
- Payment opens only at 11:45 London on a covered business day; same day only when the minimum is reached strictly before 11:00 (§12). `minimum_reached_at`, `payment_scheduled_for`, `payment_opened_at`, `pay_by`, `verify_by` are stored separately and `payment_opened_at/pay_by/verify_by` are written once (§22, §24).
- Timeliness is judged by `received_at`, never `verified_at` (§12, §18). Receipt IDs are unique per venue (case-insensitive, trimmed). Financial entries are append-only (§18).
- Only the venue confirms; only the organiser commits their club; an operator can prepare and pause but cannot commit, approve, verify payments or confirm (§08, §28).
- No member accounts, roster, access-note fields, consent forms or health fields anywhere (§19). Public venue access facts and a direct venue phone/email are shown instead.
- No state or copy says "confirmed" until venue confirmation succeeds (§13). Primary commit button text: `Commit {N} places if the session reaches {minimum}` (§07).
- Every write carries an idempotency key and a verified actor; changes to existing records carry `expected_version` (§24). Same key + same payload → original result (`replayed: true`); same key + different payload → `IDEMPOTENCY_CONFLICT`.
- HTTP (§24): 422 field errors (code `INVALID_FIELDS`), 409 stale terms / closed intake / capacity conflict, neutral 404 `NOT_FOUND` for records the caller may not see (never 403 for cross-tenant reads).
- Rejection codes reuse `CommitRejection`, `PublicationBlocker` and `ConfirmationBlocker` names from `lib/sila/*.ts` exactly.
- Do not modify `lib/sila/{time,calendar,schedule,money,session,commitment,confirmation,status}.ts` behaviour; extend only by adding exports if a task says so.
- UI: follow the existing sila design language (`components/sila/*`, `components/ui.tsx`, `app/globals.css`; reference `C:\Users\Admin\Downloads\Shared_Cultural_Bookings_Documentation_Pack\Shared_Cultural_Bookings_Pack\Design\Sila v2.dc.html`). Working screens are restrained (§30); copy follows the guide's screen text (§03, §06, §09, §10, §11, §13). WCAG 2.2 AA; touch targets ≥ 44px.
- Synthetic data only, labelled; no production deploy, no push. Commit messages: imperative, no assistant co-author trailers or tool credits (CLAUDE.md).
- Checks before a task is done: `npx tsc --noEmit`, `npm run lint`, `npm test`, and the task's DB/e2e tests (local Supabase must be running: `npx supabase start`; apply migrations with `npx supabase db reset`).

### Database conventions (every migration task)

- Tables live in `sila`; `alter table … enable row level security` on every table; no policies; `revoke all on all tables in schema sila from public, anon, authenticated`.
- Public functions: `sila_api.<name>(p_actor uuid, p_key text, …)` for actor writes, `security definer`, `set search_path = ''`, `language plpgsql`, return `jsonb` from `sila.ok(jsonb)` / `sila.err(code, message, details jsonb default '{}')` (same shape as `scb.ok/err`). Business failures are returned, not raised.
- Idempotency: `sila.idem_begin(p_actor, p_key, p_fn, p_request jsonb) returns jsonb` returns the stored result with `'replayed', true` merged into it, raises nothing, returns `sila.err('IDEMPOTENCY_CONFLICT', …)` on hash mismatch, or `null` when new; `sila.idem_finish(p_actor, p_key, p_fn, p_request, p_result) returns jsonb` stores and returns the result. Hash = `encode(extensions.digest(p_request::text, 'sha256'), 'hex')`.
- Neutral 404: unauthorised or missing → `sila.err('NOT_FOUND', 'Not found.')`.
- Grants (end of each migration): `grant usage on schema sila_api to scb_app; grant execute on all functions in schema sila_api to scb_app;` and revoke from `public, anon, authenticated`.
- Internal helpers in `sila` are not granted. Functions that need a controllable clock for tests are written as internal `sila.<name>(…, p_now timestamptz)` plus a `sila_api.<name>(…)` wrapper passing `now()`; DB tests call the internal version through the admin pool.
- Lock order for consequential writes: session row (`for update`) → plan row → allocation rows.
