# Feature Scope and MVP Prioritisation


D08 | Version 0.1 | 12 October 2026


Separate the essential release from later improvements.


Status: proposed implementation specification. Application acceptance tests remain pending.


## MVP product loop

A judge must be able to complete a genuine discovery-assisted reservation workflow. Prioritise trustworthy offers and visible human decisions before catalogue scale, automatic outreach or money movement.

| Priority | Feature | Traceability | Reason or boundary |
| --- | --- | --- | --- |
| P0 | Identity, memberships and safe judge sandbox | R01 R15 | Required before any multi-role demonstration. |
| P0 | Approved programme catalogue and exact quote snapshots | R02 | Defines deliverable supply. |
| P0 | Group brief, consent and reference disambiguation | R03 R04 | Defines demand without inferred sensitive identities. |
| P0 | Live Qloo adapter and visible provenance | R05 R06 R08 | Central hackathon dependency. |
| P0 | Bounded coalition solver and blocker explanation | R07 | Produces a viable shared candidate. |
| P0 | Versioned publication and organiser decisions | R09 R10 | Ensures everyone agrees to the same terms. |
| P0 | Reservations, readiness and atomic venue confirmation | R11 R12 R13 | Completes the product loop. |
| P0 | Privacy controls, audit and job recovery | R14 R16 R18 | Protects the demonstration and pilot. |
| P0 | Paired benchmarks and deployment checks | R17 | Supports honest impact and Qloo contribution. |
| P1 | Private member input and more detailed cultural meanings | R03 | Improves group representation after the core loop works. |
| P1 | Multiple venue workspaces and catalogue import | R02 | Add after a successful one-venue pilot. |
| Later | Payments, refunds and venue settlements | Future release | Requires provider, legal and operational design; excluded from MVP. |

| Excluded | Demographic or social-compatibility inference | None | Cultural correlation is insufficient evidence. |

## Release bounds

| Dimension | Default |
| --- | --- |
| City | Edinburgh |
| Currency | GBP |
| Eligible ages | Adults only; no date of birth required |
| Catalogue | 5 to 10 venue-approved experiences |
| Matching batch | Maximum 20 groups; 2 to 4 groups per coalition |
| Slot candidates | Maximum 5 per experience |
| Result set | Up to 3 alternatives, none published automatically |
| Commitment | One seat reservation per authenticated participant |
| Payment | NOT_COLLECTED throughout MVP |

## Cut order under time pressure

Remove voice, custom programme generation, external notifications, catalogue imports and additional cities first. Reduce catalogue size before removing safety checks. Do not cut authorisation, immutable terms, live provenance or the venue confirmation transaction.

## Post-MVP gate

Expand only after the pilot identifies an actual venue and organiser need, the booking economics leave a viable fee and Qloo shows measurable discovery value. A larger marketplace is a separate acquisition and operations problem.
